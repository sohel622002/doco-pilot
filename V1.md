# Doco-Pilot — V1 Feature Specification

*Generated from a direct audit of the codebase on 2026-09-01, branch `feat/client-ui-redesign`. Only features that are wired end-to-end (real API/WebSocket calls, real persistence) are listed as working. Anything hardcoded or unused is explicitly flagged as dummy.*

## 1. What Doco-Pilot Is

A self-hosted, multi-server Docker fleet manager, architected as three separate deployables:

| Component | Path | Stack |
|---|---|---|
| **Backend API** | `server/` | Node/Express, Supabase (Postgres) as DB, cookie-based JWT auth |
| **Web client** | `client/` | React 19, Vite, Tailwind v4, Zustand, TanStack Query, Recharts, react-hook-form + zod |
| **Agent** | `agent/` | Node process, runs on each managed host, talks to Docker via `/var/run/docker.sock`, connects outbound to the backend over WebSocket |

The backend never talks to Docker directly. The browser client connects to a WebSocket relay on the backend; the backend relays action messages to the correct host's **agent**, which executes them against the local Docker socket and streams results/events back. Historical metrics, docker events, and alert state are persisted server-side (Supabase) so charts/history survive agent disconnects.

## 2. Working Features (verified)

### 2.1 Authentication & Account (`server/routes/auth.js`, `client/src/pages/{Login,Register,ForgotPassword,ResetPassword,VerifyEmail,Profile}.jsx`)
- Email/password register + login, bcrypt password hashing, cookie-based access + refresh JWT (`utils/auth.js`, `utils/sign.js`)
- Refresh-token rotation with hashed storage (`refresh_tokens` table), single-use compare-and-delete
- Logout (revokes matching refresh token)
- Google OAuth login (authorization-code flow, account linking by email or Google ID)
- Forgot password / reset password via emailed token (Resend mail integration, `utils/mail.js`)
- Change password (invalidates all sessions)
- Email verification flow + resend-verification
- Get/update own profile (`/api/auth/me`)
- Rate limiting on auth endpoints (`middleware/rateLimiter.js`)
- Audit logging of auth/server actions (`utils/audit.js`)

### 2.2 Server (Host) Management (`server/routes/servers.js`, `client/src/pages/Servers.jsx`)
- Register a new managed server → generates unique agent key/secret (bcrypt hash stored for verification, AES-256-GCM ciphertext stored for later retrieval), returns a ready-to-run `docker run` command for the agent
- List servers owned by the logged-in user, with per-server health computed client-side from latest metrics (ok/warning/critical/unknown) and CPU/memory sparklines
- View/re-view agent credentials + install command
- Regenerate agent key/secret (revokes old agent session)
- Update server (name, IP, alert webhook URL, alert CPU threshold)
- Delete server (revokes credentials; agent container itself must be removed manually on the host)
- Server ownership enforced on every route (`user_id` scoping)

### 2.3 Live Docker Management via WebSocket (`server/ws/index.js`, `agent/src/actions.js`, `client/src/context/WebSocketContext.jsx`, `client/src/lib/actions.js`)
All of the following are real round-trips: client → backend WS relay (`server/ws/index.js`, allowlisted actions, ownership check, input sanitization, audit log) → agent → Docker Engine API (via `dockerode`) → result streamed back. The relay also samples container/system stats into `server_metrics` (≤once/min) and runs alert detection (`checkForAlert`: exit codes / CPU threshold breach → `alert_events` + outbound webhook with a 10-min cooldown).
- **Containers** (`client/src/pages/Containers.jsx`): list, start, stop, pause/unpause, restart, remove (with confirmation, blocked while running), create/deploy (`DeployContainerModal.jsx`), inspect (`InspectModal.jsx`), live logs (`LogsModal.jsx`), per-container CPU/memory/network stats polled every 5s, sortable table by CPU/memory/network
- **Images** (`client/src/pages/Images.jsx`): list, pull, remove, prune, list dangling images
- **Volumes** (`client/src/pages/Volumes.jsx`): list, inspect, remove
- **Networks** (`client/src/pages/Networks.jsx`): list, inspect, create (with driver/subnet/gateway), remove
- **System stats**: host-level CPU/memory/disk usage and uptime, polled every 5s
- Container/system state held in Zustand stores (`store/container.js`, `store/system.js`, `store/logs.js`, `store/inspect.js`), updated by `lib/websocket-handlers.js`

### 2.4 Dashboard (`client/src/pages/Home.jsx`)
- Real-time system health cards (CPU/mem/disk %, active containers) from live WebSocket system stats
- Resource usage trend chart (CPU/memory) backed by **persisted** `server_metrics` history via `GET /api/servers/:id/metrics`, selectable range (1h/24h/7d), downsampled for the 7d view
- Recent Activity feed from **persisted** `docker_events` via `GET /api/servers/:id/events` (start/stop/die/pause/unpause described in plain language)
- Server status badge (operational/degraded/critical) derived from live stats + configured CPU threshold

### 2.5 Alerts & Monitoring (`client/src/pages/Alerts.jsx`)
- Configure a webhook URL + CPU alert threshold per server (persisted, POSTed by the backend on threshold breach or container crash — `utils/webhook.js`)
- 30-day uptime percentage, computed server-side from `agent_status_events` history (`GET /api/servers/:id/uptime`)
- Live agent connection status
- Alert fire/resolve history table from persisted `alert_events` (`GET /api/servers/:id/alerts`)

### 2.6 Settings (`client/src/pages/Settings.jsx`)
- Agent installation instructions (`AgentInstallation.jsx`) — real, pulls actual generated docker command
- Danger zone: delete server (real, calls `DELETE /api/servers/:id`)

## 3. Explicitly NOT Real (dummy/placeholder — do not treat as working)

- **`EngineSection` in `Settings.jsx`**: entire "Engine & Logs" panel (engine status card, uptime "14d 2h 44m", disk usage "42.8 GB", daemon JSON editor, "Real-time Log Stream") is 100% hardcoded (`MOCK_LOGS` array, static JSX values) and is currently **commented out** of the render tree (`{/* <EngineSection /> */}`) — it renders nothing at all in the current build.
- The "Status: All" / "Stack: All" filter buttons on the Containers page are non-functional decoration (no `onClick`, no state).
- `client/src/pages/Infrastructure.jsx` was deleted in the current diff — no infra-as-code / compose feature exists.

## 4. Known Gaps / Rough Edges Observed

- **No client test coverage at all** — no test script in `client/package.json`. Server has genuine unit tests (`encryption.test.js`, `schemas.test.js`, vitest) but no route/integration tests. CI workflows do exist (`.github/workflows/agent-ci.yml`, `client-ci.yml`, `server-ci.yml`, `deploy.yml`) but only cover lint/build, not real test suites for client or agent.
- **Hardcoded placeholder values shipped to users**: `server/routes/servers.js:19-29` (`buildDockerCommand`) bakes `your-dockerhub/docker-manager-agent:latest` and a `wss://yourbackend.com` fallback into the install command shown in the UI — must be fixed before real users run it.
- **Unmanaged database migrations** — `server/supabase-schema.sql` plus four incremental `.sql` files (`001_google_oauth.sql`, `002_server_alerts.sql`, `003_metrics_events.sql`, `004_agent_status_events.sql`) applied by hand, no migration runner/versioning.
- Vestigial dead code: `client/src/lib/axios.js` still references a `localStorage` access-token key that nothing ever sets (session actually lives in httpOnly cookies).
- No RBAC — every account only ever sees/manages its own servers (`user_id` scoping); no team/multi-user sharing of a server.
- No container `exec`/shell-into-container feature.
- No image build (Dockerfile) support — only pull/remove/prune of existing images.
- No compose/stack deployment — containers are deployed one at a time via `DeployContainerModal`.
- Docs (`server/docs/openapi.yaml`) exist but should be checked for drift against actual routes.
